# 发布前脱敏记录

本技能是在**真实的稿件校稿工作**中长出来的。这既是它方法论可靠的原因
（每条铁律都来自实际踩过的坑，而不是凭空设计），也意味着它天生带着**项目痕迹**。

首次公开发布前做了一轮系统脱敏。本文记录**做法与理由**，
不列出被移除的具体内容——那本身也是不该公开的。

---

## 为什么要做

一份在多篇真实稿件上使用的技能，会不知不觉吸收四类东西：

1. **稿件识别信息** —— 期刊名、稿件号、出版商标识（如 PII）、文件名
2. **未发表的研究内容** —— 方法名、具体数值结果、图表标签、逐字引文
3. **第三方个人数据** —— 参考文献里的真实作者姓名
4. **本机环境指纹** —— 绝对路径、本机已安装的工具、临时目录

第 1、2 类最危险：它们不只是"尴尬"，而是**可能影响稿件本身**——
投稿中的稿件通常负有保密义务，提前泄露结果可能影响录用。

第 3 类常被忽略：从公开数据库（如 CrossRef）抓来的姓名虽然是公开的，
但与"某人正在校稿某篇稿件"这个事实绑定后，就成了个人信息。

---

## 做法

### 1. 案例材料整体改写为合成案例

`references/case-study.md` 原本是某篇真实稿件的完整取证记录。
现在它是**合成案例**：把多次真实校稿中反复出现的失效模式，
组装成一个连贯的教学场景；稿件、期刊、数值全部为示意。

**教训一条没少。** 案例的价值在方法论——RED（无技能）与 GREEN（有技能）的对照、
两种注意力模式为何必须分工、误报为何比漏报贵、原子化替换拦下过什么。
这些与具体是哪篇稿件无关。

### 2. 逐文件清除"可搜索的唯一字符串"

有些字符串辨识度极高——一个罕见拼写错误、一个不常见的包名、
一个特定标签名。这类串**只要残留一处**，搜索引擎就能把公开的技能仓库
与某篇具体稿件关联起来。

处理方式是**换成等价的合成实例**，而不是删掉例子：教学价值保留，
可搜索性归零。

### 3. 移除内置的学科词表

`spell.py` 原本内置了一份领域词表（方法缩写、仪器名、术语）。
两个问题：一是把技能绑死在某个学科，二是**词表本身就是高精度指纹**——
那批缩写的组合近乎唯一。

现在默认词表**只留跨学科通用词**，领域词由使用者通过
`--words my-words.txt` 或 `paper.tex.words` 外部提供。
这同时也让技能对其它领域更友好：不会读到别人学科的遗留词。

### 4. 真实姓名改为虚构姓名

文档里用来举例的第三方真实姓名（来自公开数据库的排印怪癖），
全部替换为明显虚构的名字。物证类型不变，指向的对象消失。

### 5. 量化指标泛化

有些数字本身就构成指纹——精确行数、句长统计分布、各类计数。
它们现在被换成**明确标注为示意值**的近似量级。
最有用的一行（"约 50 处真实问题 / 1700 行，硬错误约 10%"）保留，
因为它决定了预算该花在哪。

### 6. 路径与示例改为可移植

所有 `~/.claude/...`、盘符绝对路径改为相对于技能目录。
这既是为了脱敏，也是**功能性修复**——插件安装后会被复制到
`cache/` 下，写死的路径对任何消费者都不成立。

## 校验

脱敏后跑了一轮机械校验：

- 对全仓库 `grep -rniF` 若干高辨识度字符串 → **命中数为 0**
- 扫描邮箱、绝对路径、形如人名的连续首字母大写词组 → 只剩文档里
  明确标注的占位示例
- 9 个脚本全部通过语法编译

**但机械校验只能证明"已知的串不在了"**，不能证明"没有你不知道的敏感内容"。
所以发布前还有一道人工关卡：**作者本人通读一遍案例与 README**。

如果你要 fork 本仓库并加入自己的案例，建议照做同样的事——
先机械扫一遍，再自己读一遍。**自动化的 grep 替代不了人的判断。**
